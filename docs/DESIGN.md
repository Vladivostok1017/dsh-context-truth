# 设计说明

这份文档解释 `dsh-context-truth` 的取舍。想改代码前先读这里，能避免把插件改成"看起来更聪明、实际更吵"的东西。

## 1. 为什么不自己估算 token

插件用 `ctx.tokenMeter.measure(session).totalTokens` 作为分子，用
`session.requestContext().contextWindow` 作为分母。理由是**一致性**：这两个数字正是
`compaction-basic` 判定「要不要压缩」时用的东西（它调 `llm.resolveModelInfo()` 拿 `contextWindow`，
再与 `thresholdTokens` 比较）。

如果插件自己按字符数估一个百分比，会出现最坏的情况：**插件说 45%，压缩引擎说 82% 并开始压缩**。
模型收到两套互相矛盾的世界观，比不给数字更糟。因此：

- 不引入任何自定义 tokenizer 或字符密度常量；
- 不缓存窗口大小（路由/模型可能中途变化，`request/context` 是最新事实）；
- 拿不到窗口或拿不到用量时**什么都不注入**，不猜。

已知代价：`totalTokens` 含最后一条 assistant 输出，比纯 prompt 侧略大几十~几百 tokens。
相对 10⁵~10⁶ 量级可忽略，且这正是压缩判定用的同一个数，所以优先"一致"而非"精确"。

## 2. 为什么注入必须稀疏

插件本身也在消耗上下文。若每一步都注入，长会话里会把上下文推高几个百分点，还可能挤掉真正有用的内容。频率策略：

| 时机 | 注入 | 理由 |
| --- | --- | --- |
| `step === 1` | 是 | 每轮开头给一次基准读数 |
| 跨过一个 10% 刻度 | 是 | 数字真的变了，模型需要更新 |
| 进入阈值前 5% 区间 | 每步 | 这时模型确实该知道"要压缩了" |
| `/context` 挂起时 | 一次 | 人工干预，必须生效 |
| 其它 | 否 | 数字没变，重复注入只是噪音 |

副作用是"手动命令要等下一次 pre-step"。这是有意的：命令通过 `inbox.prepend('next-step')` 或
`followup()` 立即送达，挂起旗标只是送达失败时的兜底，避免同一句话进上下文两次。

## 3. 为什么检测必须保守

「假性耗尽更正」是这个插件的**唯一**会主动往对话里插话的路径，因此它的失败代价不对称：

- 漏判：模型继续拿上下文当借口 —— 用户会像以前一样手动纠正，损失可接受；
- 误判：用户正常提问/讨论中间突然出现一条 `Auto-correction`，看起来像插件抽风 —— 破坏信任。

所以判定做成四条件合取，且先做正文净化：

1. **净化**：剥掉围栏代码块、行内代码、成对引号（`"…"` `“…”` `「…」` `『…』` `'…'`，单引号只在
   "像引号的位置"成对剥，以免吃掉 `I'm` / `don't` 里的撇号）、Markdown 块引用。
   动机：对话和文档里**引用**这类句子极其常见（"上一轮你说过『我的上下文已经用完』"），
   而引用不是自述。
2. **元话语过滤**：整条消息若在讨论检测器本身（`claimsContextExhaustion`、`assert.equal`、
   `selftest`、`测试用例`、`回归用例`、`false positive`、`误报`），直接跳过。
   动机：调试这个插件的人（包括 AI agent）必然会把这些句子写进消息里。
3. **四条件合取**：断言命中 + 第一人称 + 停止意图 + 排除否定语境。

其中「停止意图」是最关键的一条：模型描述用量（"已用 45%"）时不该触发，只有把上下文
**当作停止理由**（不再/无法/不做/交接/wrap up/must stop）才是这个插件要纠正的行为。

任何放宽上述规则的改动，都必须同时补上"引用/举例/代码字符串不命中"的回归用例。

## 4. 送达策略

`/context` 要解决的是"模型已经停下或者正在跑，但自动注入还没到"。三种送达方式按可达性降级：

| 优先级（运行中 / 空闲） | 手段 | 语义 |
| --- | --- | --- |
| 1 / 2 | `agent.inbox.prepend('next-step', msg)` | 直接进当前 turn 的下一步 |
| 2 / 1 | `agent.followup(msg)` | 排队成下一轮的输入（空闲时会开启一轮） |
| 兜底 | 挂起旗标 | 下一次 pre-step 无条件注入一次 |

**任一条成功即停止**。两条都调会造成同一段文字在上下文里出现两次，既浪费又像 bug。
`commandMode: queue` 可让默认行为只挂起、不主动开轮。

## 5. 与宿主 loader 的约束

- 插件以 `dsh.bundle.patch` 声明自己是一个 profile layer，安装后进 `dsh.profile.bundles`；
- **loader entry id 必须全局唯一**。同一个 id 被 bundle 与 `$DSH_HOME/cordis.patch.yml` 各插一次，
  冷启动会在 `validate` 阶段抛 `duplicate loader entry id` 并让整棵插件树加载失败——
  这是启动错误，运行时仲裁救不了；
- 因此运行时的 `Symbol.for('dsh-context-truth.mount')` 仲裁只处理"**不同 id** 挂载了同一插件"
  的情况（例如 bundle + 一个换了 id 的 `file://` 热挂载）：后加载的实例让位并打 warn。
- `inject = ['tokenMeter', 'commands']`：服务缺失时插件不激活，而不是静默降级。

## 6. 只读边界

插件只做三件事：`agent/pre-step` 追加消息、注册命令、进程级挂载标记。它**不**：

- 修改模型输出或历史；
- 触发、阻止或配置压缩（阈值只读，不写）；
- 写任何宿主文件或配置文件。

`state` 只存内存里每会话一条小记录，超过 500 个会话按 FIFO 淘汰，避免长开进程无界增长。
